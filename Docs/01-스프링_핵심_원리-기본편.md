# 스프링 핵심 원리 - 기본편

## 개요 및 객체 지향 설계 원칙

### 자바 진영의 역사적 배경과 스프링의 탄생

2000년대 초반 자바 엔터프라이즈 개발의 표준이었던 EJB(Enterprise JavaBeans)는 높은 기술적 복잡도, 강한 결합도, 느린 실행 속도로 인해 개발 생산성을 현저히 떨어뜨렸다.  
개발자들은 EJB 프레임워크 기술에 종속된 코드가 아닌, 순수한 자바 객체(POJO: Plain Old Java Object)로 복잡한 비즈니스 로직을 구현하고자 하는 열망을 가지게 되었다.

이러한 배경 속에서 Rod Johnson이 출간한 책에 포함된 유연한 예제 코드가 모태가 되어 '겨울(EJB)이 지나고 봄이 왔다'는 의미의 **스프링(Spring) 프레임워크**가 탄생했다.

### 좋은 객체 지향 설계의 5가지 원칙 (SOLID)

객체 지향 프로그래밍의 핵심인 다형성(Polymorphism)을 넘어, 시스템의 변경과 확장에 유연하게 대처하기 위해서는 SOLID 원칙을 준수해야 한다.

| 원칙      | 명칭                                            | 핵심 개념 및 의의                                                                                                       |
| ------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **SRP** | 단일 책임 원칙 (Single Responsibility Principle)    | 한 클래스는 단 하나의 책임만 가져야 한다. 변경의 축이 되는 것은 '책임'이며, 코드 변경 시 파급 효과가 적어야 SRP를 잘 준수한 것이다.                                 |
| **OCP** | 개방-폐쇄 원칙 (Open/Closed Principle)              | 소프트웨어 요소는 **확장에는 열려 있으나 변경에는 닫혀 있어야 한다**. 다형성을 활용하여 인터페이스를 구현한 새로운 클래스를 만들어 기능을 확장하면서, 기존 클라이언트 코드는 수정하지 않아야 한다. |
| **LSP** | 리스코프 치환 원칙 (Liskov Substitution Principle)    | 프로그램의 객체는 프로그램의 정확성을 해치지 않으면서 하위 타입의 인스턴스로 바꿀 수 있어야 한다. 단순히 문법적 상속을 넘어, 규약 및 의도에 부합하는 하위 클래스를 작성해야 한다.           |
| **ISP** | 인터페이스 분리 원칙 (Interface Segregation Principle) | 특정 클라이언트를 위한 인터페이스 여러 개가 범용 인터페이스 하나보다 낫다. 인터페이스가 명확해지고, 대체 가능성이 높아진다.                                           |
| **DIP** | 의존관계 역전 원칙 (Dependency Inversion Principle)   | 프로그래머는 **"추상화에 의존해야지, 구체화에 의존하면 안된다"**. 즉, 구현 클래스가 아닌 인터페이스(역할)에 의존해야 유연하게 구현체를 변경할 수 있다.                        |

## 순수 자바 기반 도메인 설계와 한계

스프링 프레임워크의 도우미 없이 순수 자바 코드로 회원 가입/조회 기능과 주문/할인 정책 도메인을 개발해보며 객체 지향 설계의 한계를 파악해본다.

### 도메인 요구사항 및 설계

* **회원 도메인**: 회원 가입 및 조회가 가능하며, 일반(BASIC)과 VIP 등급이 존재함. 회원 저장소는 메모리 DB, RDB, 외부 시스템 연동 등이 가능하도록 인터페이스 기반 분리.
* **주문 및 할인 도메인**: 회원은 상품을 주문할 수 있으며, VIP 회원에 한해 할인 정책 적용.  
  * 고정 금액 할인 정책 (`FixDiscountPolicy`): VIP에 대해 1,000원 고정 할인.
  * 정률 금액 할인 정책 (`RateDiscountPolicy`): VIP에 대해 주문 금액의 10% 비율 할인.

### 순수 자바 구현 시 발생하는 문제점 (OCP/DIP 위반)

초기 주문 서비스 구현체 `OrderServiceImpl`은 고정 할인 정책을 적용하기 위해 다음과 같이 작성되었다.

```java
public class OrderServiceImpl implements OrderService { 
    private final MemberRepository memberRepository = new MemoryMemberRepository(); 
    private final DiscountPolicy discountPolicy = new FixDiscountPolicy(); 

    @Override 
    public Order createOrder(Long memberId, String itemName, int itemPrice) { 
        Member member = memberRepository.findById(memberId); 
        int discountPrice = discountPolicy.discount(member, itemPrice); 
        return new Order(memberId, itemName, itemPrice, discountPrice); 
    } 
}
```

이후 기획자의 요구사항 변경에 따라 정률 할인 정책(`RateDiscountPolicy`)으로 교체하고자 할 때 심각한 문제점이 발생한다.

```java
public class OrderServiceImpl implements OrderService { 
    private final MemberRepository memberRepository = new MemoryMemberRepository(); 
    // private final DiscountPolicy discountPolicy = new FixDiscountPolicy(); 
    private final DiscountPolicy discountPolicy = new RateDiscountPolicy(); 
}
```

#### 발생한 문제의 원인 분석

1. **DIP 위반**: `OrderServiceImpl`은 `DiscountPolicy` 인터페이스뿐만 아니라, 구체 클래스인 `FixDiscountPolicy`와 `RateDiscountPolicy`에도 직접 의존하고 있다.
2. **OCP 위반**: 할인 정책을 변경하는 순간, 사용 영역인 클라이언트 코드 `OrderServiceImpl`의 소스 코드를 직접 수정해야 하므로 확장에는 열려있으나 변경에 닫혀있어야 한다는 원칙을 깨뜨린다.

## 관심사의 분리와 IoC / DI 컨테이너

### 관심사의 분리 (Separation of Concerns)와 `AppConfig`

기존 코드는 클라이언트 객체가 실행 책임과 객체 생성/연결 책임을 동시에 지고 있었다.

이를 해결하기 위해 애플리케이션의 전체 동작 방식을 구성(Configuration)하는 **관리자 역할의 `AppConfig`**를 도입한다.

```java
public class AppConfig { 
    public MemberService memberService() { 
        return new MemberServiceImpl(memberRepository()); 
    } 

    public OrderService orderService() { 
        return new OrderServiceImpl(memberRepository(), discountPolicy()); 
    } 

    public MemberRepository memberRepository() { 
        return new MemoryMemberRepository(); 
    } 

    public DiscountPolicy discountPolicy() { 
        // 구성 영역만 수정하여 전체 애플리케이션 행동 변경 
        return new RateDiscountPolicy(); 
        // return new FixDiscountPolicy();
    } 
}
```

### 생성자 주입을 통한 해결

`OrderServiceImpl`은 이제 구체 클래스를 전혀 알지 못하며, 오직 `DiscountPolicy` 및 `MemberRepository` 인터페이스에만 의존한다.


```java
public class OrderServiceImpl implements OrderService { 
    private final MemberRepository memberRepository; 
    private final DiscountPolicy discountPolicy; 

    public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) { 
        this.memberRepository = memberRepository; 
        this.discountPolicy = discountPolicy; 
    } 

    @Override 
    public Order createOrder(Long memberId, String itemName, int itemPrice) { 
        Member member = memberRepository.findById(memberId); 
        int discountPrice = discountPolicy.discount(member, itemPrice); 
        return new Order(memberId, itemName, itemPrice, discountPrice); 
    } 
}
```

### IoC, DI 및 컨테이너 핵심 개념

* **제어의 역전 (IoC, Inversion of Control)**: 프로그램의 제어 흐름을 클라이언트가 아닌 외부(`AppConfig`)가 관리하는 원칙이다.
* **의존관계 주입 (DI, Dependency Injection)**: 애플리케이션 실행 시점(런타임)에 외부에서 실제 구현 객체를 생성하고 클라이언트에 전달하여 의존관계를 연결하는 메커니즘이다.
* **의존관계 분리**:  
  * **정적인 클래스 의존관계**: 클래스 내 `import` 코드만으로 분석할 수 있는 의존관계.
  * **동적인 객체 인스턴스 의존관계**: 런타임에 실제 생성된 객체 참조가 연결되는 의존관계.


## 스프링 컨테이너와 스프링 빈

### 스프링 컨테이너 (`ApplicationContext`)

`ApplicationContext`를 스프링 컨테이너라 부르며, `@Configuration`이 붙은 `AppConfig`를 설정 정보로 사용하여 `@Bean` 메서드가 반환하는 객체들을 스프링 빈으로 등록 및 관리한다.

```java
ApplicationContext applicationContext = new AnnotationConfigApplicationContext(AppConfig.class); 
MemberService memberService = applicationContext.getBean("memberService", MemberService.class);
```

### `BeanFactory` vs `ApplicationContext`

* **`BeanFactory`**: 스프링 컨테이너의 최상위 인터페이스로, 빈 관리 및 조회 기능(`getBean()`)을 제공한다.
* **`ApplicationContext`**: `BeanFactory`의 모든 기능을 상속받고, 엔터프라이즈 환경에 필요한 부가 기능을 추가로 제공한다.
  * `MessageSource`: 메시지소스를 활용한 국제화 기능.
  * `EnvironmentCapable`: 로컬, 개발, 운영 등 환경변수 구분 관리.
  * `ApplicationEventPublisher`: 이벤트 발행 및 구독 모델 지원.
  * `ResourceLoader`: 파일, 클래스패스, 외부 리소스 편리한 조회.

### 메타정보 추상화: `BeanDefinition`

스프링은 다양한 설정 형식(자바 코드, XML, Groovy 등)을 지원하기 위해 `BeanDefinition`이라는 메타정보 추상화를 사용한다.  
스프링 컨테이너는 설정 정보가 자바 코드인지 XML인지 알 필요 없이 오직 `BeanDefinition`만 참조하여 빈을 생성한다.

## 싱글톤 컨테이너와 CGLIB

### 싱글톤 컨테이너의 필요성

웹 애플리케이션은 보통 수많은 고객의 동시에 발생하는 요청을 처리한다.   
스프링 없는 순수 DI 컨테이너는 요청마다 새로운 객체를 생성하므로 초당 100건의 요청 시 100개의 객체가 생성/소멸되어 메모리 낭비가 심각하다.

스프링 컨테이너는 객체 인스턴스를 단 1개만 생성하여 공유하는 **싱글톤 레지스트리(Singleton Registry)** 로 동작한다.

### 싱글톤 방식의 치명적 주의점: 무상태(Stateless) 설계

여러 클라이언트가 하나의 객체 인스턴스를 공유하므로, 싱글톤 객체는 반드시 **무상태(Stateless)** 로 설계해야 한다.

```java
// BAD: 상태를 유지하는 필드가 존재하는 경우 (장애 발생 코드) 
public class StatefulService { 
    private int price; // 공유되는 상태 필드 

    public void order(String name, int price) { 
        this.price = price; // 특정 클라이언트가 값을 변경함! 
    } 

    public int getPrice() { 
        return price; 
    } 
}
```

#### 해결책

공유 필드 대신 지역변수, 파라미터, `ThreadLocal` 등을 사용해야 한다.

```java
// GOOD: 무상태 설계 
public class StatelessService { 
    public int order(String name, int price) { 
        return price; // 파라미터와 반환값을 활용 
    } 
}
```

### `@Configuration`과 CGLIB 바이트코드 조작

`AppConfig` 코드를 보면 `memberRepository()` 메서드가 여러 번 호출되어 싱글톤이 깨질 것처럼 보인다.

```java
@Configuration 
public class AppConfig { 
    @Bean 
    public MemberService memberService() { 
        return new MemberServiceImpl(memberRepository()); 
    } 

    @Bean 
    public OrderService orderService() { 
        return new OrderServiceImpl(memberRepository(), discountPolicy()); 
    } 

    @Bean
    public MemberRepository memberRepository() { 
        return new MemoryMemberRepository(); 
    } 
}
```

스프링은 CGLIB(Code Generator Library) 바이트코드 조작 라이브러리를 통해 `AppConfig`를 상속받은 임의의 프록시 클래스(`AppConfig$$EnhancerBySpringCGLIB`)를 만들어 빈으로 등록한다.


```java
// CGLIB 프록시의 오버라이딩 오퍼레이션 내부 의도 코드 
@Bean 
public MemberRepository memberRepository() {
    if (alreadyInSpringContainer("memberRepository")) { 
        return getFromSpringContainer("memberRepository"); 
    } else { 
        MemberRepository repo = super.memberRepository();
        registerInSpringContainer("memberRepository", repo); 
        return repo; 
    }
}
```

만약 `@Configuration`을 붙이지 않고 `@Bean`만 사용할 경우, 자바 코드 그대로 매번 new 객체가 생성되어 싱글톤이 보장되지 않는다.

## 컴포넌트 스캔과 의존관계 자동 주입

### 컴포넌트 스캔 (`@ComponentScan`)

설정 정보 클래스에 `@ComponentScan`을 붙이면, `@Component` 애노테이션이 붙은 클래스들을 자동으로 탐색하여 스프링 빈으로 등록한다.

- **스캔 대상 기본 애노테이션**:  
  - `@Component`: 기본 스캔 대상.
  - `@Controller`: 스프링 MVC 컨트롤러로 인식.
  - `@Service`: 비즈니스 로직 계층 표시.
  - `@Repository`: 데이터 접근 계층으로 인식하고, 데이터베이스 관련 예외를 스프링의 추상화된 예외로 변환.
  - `@Configuration`: 스프링 설정 정보로 인식 및 CGLIB 싱글톤 유지.

### 기본 스캔 위치 설정 베스트 프랙티스

`basePackages`를 직접 지정하기보다는, 설정 정보 클래스(`@SpringBootApplication`)를 프로젝트 최상단 루트 패키지에 두는 방식을 권장한다.

### 빈 이름 중복 충돌

1. **자동 빈 vs 자동 빈**: `ConflictingBeanDefinitionException` 예외 발생.
2. **수동 빈 vs 자동 빈**: 과거에는 수동 빈이 오버라이딩했으나, 최근 스프링 부트에서는 오버라이딩을 금지하고 오류를 발생시키는 것을 기본값으로 설정함.

## 의존관계 자동 주입의 심화

### 4가지 의존관계 주입 방식

1. **생성자 주입 (Constructor Injection)** — **권장!**  
  * 생성자 호출 시점에 딱 1번만 호출됨이 보장.
  * **불변**, **필수** 의존관계에 사용.
  * `final` 키워드를 사용할 수 있어 초기화 누락을 컴파일 시점에 방지.
  * 생성자가 단 1개만 존재할 경우 `@Autowired` 생략 가능.
2. **수정자 주입 (Setter Injection)**  
  * 선택, 변경 가능성이 있는 의존관계에 사용.
3. **필드 주입 (Field Injection)**  
  * 외부 변경이 불가능하여 단위 테스트 작성이 극도로 어려우므로 **사용 금지**.
4. **일반 메서드 주입 (Method Injection)**  
  * 한 번에 여러 필드를 주입받을 수 있으나 잘 사용되지 않음.

### Lombok `@RequiredArgsConstructor` 활용

Lombok 라이브러리는 `final`이 붙은 필드를 모아 컴파일 시점에 생성자 코드를 자동으로 생성해준다.

```java
@Component 
@RequiredArgsConstructor 
public class OrderServiceImpl implements OrderService { 
    private final MemberRepository memberRepository; 
    private final DiscountPolicy discountPolicy;
}
```

### 조회 빈이 2개 이상일 때의 해결책

`@Autowired`는 타입(Type)으로 조회하므로, `DiscountPolicy`의 하위 타입인 `FixDiscountPolicy`와 `RateDiscountPolicy`가 모두 빈으로 등록되면 `NoUniqueBeanDefinitionException`이 발생한다.

#### 해결 방법 3가지

1. **`@Autowired` 필드 명 매칭**: 먼저 타입 매칭을 시도하고, 결과가 2개 이상이면 필드 이름이나 파라미터 이름으로 추가 매칭한다.
  ```java
  @Autowired 
  private DiscountPolicy rateDiscountPolicy;
  ```
2. **`@Qualifier` 사용**: 추가 구분자를 붙여주는 방식이다.
  ```java
  @Component 
  @Qualifier("mainDiscountPolicy") 
  public class RateDiscountPolicy implements DiscountPolicy {}
 
  @Autowired 
  public OrderServiceImpl(MemberRepository memberRepository, @Qualifier("mainDiscountPolicy") DiscountPolicy discountPolicy) { 
      this.memberRepository = memberRepository; 
      this.discountPolicy = discountPolicy; 
  }
  ```
  
3. **`@Primary` 사용** — **우선 적용 권장**: 우선순위를 지정하여 여러 빈이 매칭될 때 최우선 선택되도록 한다.
  ```java
  @Component 
  @Primary 
  public class RateDiscountPolicy implements DiscountPolicy {}
  ```

> **우선순위**: 상세하게 작용하는 `@Qualifier`가 기본값처럼 동작하는 `@Primary`보다 높다.

### 전략 패턴 구현: `List`, `Map` 주입

해당 타입의 모든 빈을 다 다루어야 할 때 컬렉션으로 주입받을 수 있다.

```java
public class AllBeanTest { 
    static class DiscountService { 
        private final Map<String, DiscountPolicy> policyMap;
        private final List<DiscountPolicy> policies;

        public DiscountService(Map<String, DiscountPolicy> policyMap, List<DiscountPolicy> policies) {
            this.policyMap = policyMap; 
            this.policies = policies;
        }

        public int discount(Member member, int price, String discountCode) { 
            DiscountPolicy discountPolicy = policyMap.get(discountCode); 
            return discountPolicy.discount(member, price); 
        }
    }
}
```

### 실무 빈 등록 기준 (자동 vs 수동)

* **업무 로직 빈**: 컨트롤러, 서비스, 리포지토리 등은 수가 많고 일반적인 패턴이 있으므로 **자동 등록(`@Component`)** 을 사용.
* **기술 지원 빈**: DB 연결, AOP 처리 등 애플리케이션 전반에 영향을 미치는 핵심 기술 객체는 **수동 등록(`@Configuration` + `@Bean`)** 을 통해 명확히 드러내는 것이 유지보수에 유리함.
* **다형성을 적극 활용하는 비즈니스 로직**: 한눈에 주입 대상 빈을 파악할 수 있도록 별도의 수동 설정 클래스로 관리하거나 동일 패키지에 배치.

## 빈 생명주기 콜백

스프링 빈은 **객체 생성 → 의존관계 주입**의 단계를 거친 후에야 필요한 데이터를 사용할 준비가 완료된다.

### 빈 이벤트 라이프사이클

스프링 컨테이너 생성 -> 스프링 빈 생성 -> 의존관계 주입 -> **초기화 콜백** -> 사용 -> **소멸전 콜백** -> 스프링 종료

> **객체 생성과 초기화의 분리**: 생성자는 메모리 할당 및 파라미터 수신 책임만 가져야 하며, 외부 커넥션 연결 등 무거운 초기화 작업은 초기화 콜백 메서드로 분리하는 것이 관리에 용이하다.

### 3가지 생명주기 콜백 방식 비교

| 구분              | 인터페이스 (`InitializingBean`) | `@Bean(initMethod, destroyMethod)` | `@PostConstruct`, `@PreDestroy` |
| --------------- | -------------------------- | ---------------------------------- | ------------------------------- |
| **적용 방식**       | 인터페이스 상속 구현                | 설정 정보에 메서드명 지정                     | 애노테이션 부착                        |
| **스프링 종속성**     | 종속적 (스프링 전용 코드)            | 비종속적                               | 비종속적 (자바 표준 JSR-250 / Jakarta)  |
| **외부 라이브러리 적용** | 불가                         | **가능**                             | 불가                              |
| **종료 메서드 추론**   | 없음                         | 지원 (`close`, `shutdown` 자동 탐색)     | 없음                              |
| **실무 권장도**      | 사용 안 함 (초창기 방식)            | 외부 라이브러리용 사용                       | **최우선 권장**                      |

## 빈 스코프 (Bean Scopes)

### 스코프의 종류

* **싱글톤 (Singleton)**: 기본 스코프. 컨테이너의 시작과 종료까지 유지.
* **프로토타입 (Prototype)**: 빈의 생성, 의존관계 주입, 초기화까지만 관여하고 이후 관리하지 않는 스코프 (종료 콜백 호출 안 됨).
* **웹 스코프 (Web Scope)**:  
  * `request`: HTTP 요청 하나가 들어오고 나갈 때까지 유지.
  * `session`: HTTP Session 생명주기와 동일.
  * `application`: 서블릿 컨텍스트(`ServletContext`)와 동일.
  * `websocket`: 웹 소켓 생명주기와 동일.

### 싱글톤 빈과 프로토타입 빈을 함께 사용할 때의 문제와 해결

싱글톤 빈 내부에 프로토타입 빈이 주입될 경우, 주입 시점에만 새로 생성되고 이후 싱글톤 빈과 함께 계속 유지되는 문제가 발생한다.

#### DL(Dependency Lookup) 해결책: `ObjectProvider` & JSR-330 `Provider`

필요한 시점에 컨테이너에서 빈을 탐색하도록 처리한다.

```java
// 1. ObjectProvider (스프링 전용) 
@Autowired 
private ObjectProvider<PrototypeBean> prototypeBeanProvider; 

public int logic() { 
    PrototypeBean prototypeBean = prototypeBeanProvider.getObject(); // DL 
    prototypeBean.addCount(); 
    return prototypeBean.getCount(); 
}

// 2. jakarta.inject.Provider (자바 표준 - 스프링 부트 3.0 이상) 
@Autowired 
private Provider<PrototypeBean> provider; 

public int logic() { 
    PrototypeBean prototypeBean = provider.get(); // DL 
    prototypeBean.addCount(); 
    return prototypeBean.getCount(); 
}
```

### 웹 request 스코프와 프록시

HTTP 요청이 올 때 생성되는 `request` 스코프 빈을 애플리케이션 시작 시점에 싱글톤 빈에 주입하려고 하면 에러가 발생한다.

#### 해결방안: CGLIB 프록시 (`proxyMode`)

`@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)` 설정을 추가하면, 스프링은 CGLIB를 통해 가짜 프록시 객체를 만들어 미리 주입해 둔다.

```java
@Component 
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS) 
public class MyLogger { 
    private String uuid; 
    private String requestURL; 
    
    @PostConstruct 
    public void init() { 
        uuid = UUID.randomUUID().toString(); 
    } 
}
```

가짜 프록시 객체는 실제 요청이 들어오면 그때 내부에서 진짜 빈을 찾는 위임 로직을 수행한다.  
클라이언트는 마치 싱글톤 빈을 사용하듯이 편리하게 웹 스코프 빈을 활용할 수 있다.
